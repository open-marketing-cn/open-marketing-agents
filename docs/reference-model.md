# 参考范式：Agency Agents、Open Design 与 Open Marketing

## 一句话结论

Open Marketing v0.1 采用 **Agency Agents 的“看目录、看详情、选目标、安装”产品入口**，采用 **Open Design 的“本地 CLI 负责执行、能力以文件系统包交付”底层方向**，但增加中国营销工作必须有的输入、证据、权限、人工确认和真实验证门槛。

## 相同与不同

| 维度 | Agency Agents | Open Design | Open Marketing v0.1 |
|---|---|---|---|
| 第一任务 | 找到并安装一个角色 Agent | 在本地 Agent 中完成设计工件 | 找到并安装一个具体营销任务 Agent |
| 主要用户 | 使用编码 Agent 的知识工作者 | 设计/开发用户 | 中国营销从业者、品牌操盘手、小团队 |
| 内容单位 | Agent 人设/指令 | Skill、Plugin、Template、Design System | Agent、内置 Skill、数据连接器；Workflow 延后 |
| 桌面结构 | 目录、工具、项目、团队、活动 | Home、Studio、Automation、Design System、Plugin | 先只做六阶段 Agent 商店与安装详情 |
| 执行位置 | Claude Code、Codex、Cursor 等 | 本地 CLI 或 BYOK 模型 | v0.1 只开放 Codex；桌面应用负责安装和调度 |
| 安装范围 | 全局或项目、多个工具 | CLI/MCP 与本地包 | v0.1 只支持 Codex 全局 Skill 目录 |
| 中国语境 | 有部分中国渠道 Agent | 主要面向设计生产 | 中文任务、国内平台、常用数据、交付物和人工确认 |
| 状态门槛 | 是否安装 | 是否可运行/可渲染 | 共创中、待验证、可安装；未验证前前后端双重禁止 |
| 验证 | 内容作者与社区使用 | 自动测试、渲染/运行能力 | Codex 技术验证 + 真实中国营销从业者脱敏任务验证 |
| 数据边界 | 以 Agent 文件为主 | 本地优先，插件/MCP 扩展 | 原始数据进当前项目 `.open-marketing/`，凭证不进仓库/运行记录 |
| 自动动作 | 取决于 Agent | 可运行完整设计循环 | 首发不自动发布、投放、私信、付款或修改平台后台 |

## 为什么不直接套壳

直接复制 UI 和角色列表只能得到“看起来很完整”的营销 Agent 收藏夹，不能回答营销人真正会问的五件事：

1. 我必须提供什么？
2. 它到底会交付什么文件？
3. 哪些内容没有证据、不能推断？
4. 哪一步仍然要我或负责人决定？
5. 谁真实用过，这个版本是否真的有用？

因此 Open Marketing 复用机制和兼容许可证内容，但使用自己的清单、状态机、验证记录和中文工作结构。

## 为什么先参考 Agency Agents，再参考 Open Design

Agency Agents 更接近 v0.1 的首要动作：普通用户打开桌面应用，搜索一个 Agent，选择 Codex，然后安装。它适合帮助我们把商店和安装体验做透。

Open Design 已经扩展成设计生产平台，包含项目、工件、自动化、插件、渲染和多工具适配。它更适合作为后续架构参照：当 Open Marketing 增加项目底稿、Agent 串联、交付物预览和连接器时，再逐步借鉴其文件系统包、运行时适配器和本地优先机制。v0.1 不复制这套复杂度。

## 对 Open Marketing 的直接落地

- 左侧不是抽象“房间”，而是六个营销工作空间。
- 中间先显示 Agent，Skill 作为第二层；内置 Skill 默认隐藏。
- 右侧固定显示任务、输入、交付物、不能判断、人工确认、权限、验证和来源。
- 只检测 Codex CLI 与 Codex.app；其他工具后续可以显示“待验证”，但不开放安装。
- 每个上游候选先进入“共创中”，不会因为来自成熟仓库就自动变成可安装。
- 相同任务合并为一个本土化 Open Marketing 版本，并保留多个来源。
- 上游更新进入人工审阅，不自动覆盖本土化内容。

## 以后什么时候增加闭环

只有当同一垂直营销场景中至少两个 Agent 已被真实验证，而且前一个交付物字段能稳定成为后一个的输入，才增加 Workflow。闭环不是 v0.1 的宣传口号；它必须由真实交付物合同支持。
