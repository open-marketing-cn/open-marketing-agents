# 共同维护手册

目标不是把更多链接搬进来，而是每周把 5 个候选变成可复核的实战记录，每月把至少 10 个真正能被别人复用的 Skill 公开出来。

## 两个系统的职责

- **飞书**：对社区开放一个“推荐一个 Skill”表单和一个白名单字段的只读推荐广场；认领、实践、同类横评和审核都在维护后台流转，正式底表不向公众开放。
- **GitHub**：正式 manifest、来源 Commit、评判记录和网站发布版本；只有人工复核后的 PR 才能改变公开结论。

自动化只能新增推荐信号、回写机器检查结果或更新上游快照。它不得覆盖人工案例、实践经验、公开授权、退回原因或最终审核结论。同一候选以“标准化仓库 URL + Skill 路径”去重，重复推荐只追加信号。

网站推荐预览按小时读取“推荐广场”视图。仓库必须配置 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 和 `FEISHU_PUBLIC_VIEW_ID`；密钥只放 GitHub Actions Secrets。首次未配置完整密钥时部署沿用仓库内最后一次安全快照；一旦三项齐全，任何同步失败都会停止本次部署，避免发布空数据。

## 同类 Skill 怎么对比

- 只把解决**同一个具体任务**的 Skill 放进同一组，例如“生成演示文稿”，而不是把整个“创意内容”赛道放进一张表；
- 两个 Skill 即可建立对比组，公开页先说明“各自把什么做深了”和“共同边界”，再展示六维画像、工作方式和证据；不替用户做 A / B 选择；
- 一张左右对比表最多放 4 个候选。达到 5 个时，先按交付物、运行环境和使用前提筛成 2–4 个，再进入横评；
- 不做脱离任务的总分榜。门槛、稳定性、自由度、操作者依赖、素材依赖和工作流完整度都只是取舍；
- 结论必须标记项目方说明、维护者实测、社区案例或待验证推断，并写核验日期；
- 同组候选使用同一 Brief，记录运行环境、操作者水平、参考质量、修改轮次和最终成果。没有统一 Brief 时可以展示来源判断，但必须明确标为“实践待补”。

## 每周节奏

### 周一：发现与去重

- 从 GitHub Trending（weekly）、营销主题仓库、OpenSEO 和 Feishu 候选池各找一批，先去重；
- 每个候选先登记来源、真实 SKILL.md 路径、许可证、适用营销阶段和依赖；
- 当周先找够候选，周五至少提交 5 份带完整实战证据的评判记录；只看过源码的条目不计入。

### 周二至周四：实践与补证据

- 维护者给候选分配一个统一 Brief 和一位实践者；
- 实践者只使用脱敏/虚构资料，记录输入、动作、输出、人工决定和证据；
- 补齐至少两个使用场景、适用边界、不适用反例、入门到进阶路径、弯路、最佳实践和二创；
- 不能完成实践的记录保持 needs_practice，不用“看过源码”代替。

### 周五：评判与提交

- 运行 npm run catalog:evaluate -- --include-public；
- 逐条人工确认来源、许可证、独立性、安全和隐私；
- 只有 ready_for_publication 才开 PR；PR 合并后才计入月度公开数；
- 周报记录本周 5 条目标完成情况、退回原因、下周补证据的人和条目。

## 分工

- **发现者**：负责候选来源、去重和第一版任务描述；
- **实践者**：负责统一 Brief、案例、使用深度和踩坑记录；
- **复核者**：负责来源、许可证、安全、隐私和边界，不以作者名气替代证据；
- **合并者**：负责 manifest、PR、署名和发布日期，确认公开卡片与上游原文边界。

一人可以兼任多个角色，但案例作者和最终复核者最好不是同一个人；这样更容易发现“自己觉得好用、别人跑不起来”的问题。

## 计数口径

- 提交数：全部 gate 通过、带来源、案例、署名、实践细节并进入人工复核队列的唯一 Skill；
- 公开数：所有 gate 通过、PR 已人工合并且详情页显示实践资料的 Skill；
- 退回、重复链接、只有截图/Star、没有实践者署名的条目不计数；
- 当周少于 5 条或当月少于 10 条时，公开报告缺口和原因，不降低收录标准。

## 案例隐私

案例默认脱敏。不得提交客户名称、真实账号、Token、内部路径、未获授权的群聊或原始素材；证据链接只需让维护者核验关键事实。案例公开前由实践者确认可公开范围。

## 发布与回写

1. 唯一的飞书推荐表进入“社区推荐入口”，先检查垃圾链接、脱敏授权和重复候选；
2. 维护者核验来源后，将候选转入内部“推荐信号”，生成稳定 ID 并决定是否邀请实测；
3. 认领、统一 Brief、实践补证和同类横评由维护者在后台记录，评判 Agent 只生成建议；
4. 人工决定是否开 PR，并把飞书评判记录关联到 Git Commit；
5. PR 合并、网站部署验证成功后，才把飞书状态改为“已发布”并写入网站链接；
6. 若网站发布失败，飞书不得提前显示“已发布”。

公众视图不得包含联系方式、内部评语、机器原始日志和未授权材料。分享权限变化后必须用匿名窗口验证；“维护者本人能打开”不等于公众可访问。
