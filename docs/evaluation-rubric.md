# Open Marketing Skill 评判协议

这份协议用于判断一个候选 Skill 是否值得进入公开目录。这里的“好用”不是链接存在，也不是 Star 多，而是第三方能按说明跑起来、得到可交接结果，并知道真实使用中的弯路。评判输出必须能回答：

> 它是否真的能独立完成一个明确的品牌营销任务，并留下可交接、可复核的结果？

## 收录必备的实战资料

每个公开 Skill 都必须同时带以下资料；缺任何一项就留在候选池，不以“以后补”计入好用 Skill：

现有目录条目不因规则升级而被静默删除，会显示“实战待补”；在案例和深度复核完成前，它们不计入每月 10 个好用 Skill。

- **案例**：至少一个真实或脱敏案例，写清背景、输入、执行动作、输出和证据链接；
- **署名**：上游作者/仓库署名 + 实际实践者署名（可写“某消费品牌 SEO 负责人”等匿名角色）；
- **玩起来**：安装、准备材料、第一条提示词、预期输出和人工接手点；
- **弯路**：实际失败、误判、依赖未满足或不适用的情况；
- **最佳实践**：实践后形成的检查表、提示词改法或工作流顺序；
- **二创**：如果改了提示词、模板、字段或中文场景，说明改了什么、为什么改、与上游的边界。
- **深度**：至少两个具体使用场景，写清适用边界、明确不适用的情况，以及从入门到进阶的玩法路径。

建议用统一的 `practiceEvidence` 字段记录这些内容：

`caseTitleZh`、`contextZh`、`inputZh`、`outputZh`、`evidenceUrl`、`practitionerRole`、`attributionZh`、`howToUseZh`、`setupZh`、`expectedOutputZh`、`pitfallsZh`、`bestPracticesZh`、`remixZh`、`scenariosZh`、`boundaryZh`、`notForZh`、`depthPathZh`。

案例可以脱敏，但不能只放截图或一句“已验证”；证据应能让维护者复核，且不泄露客户机密。

## 决策不是平均分

评判器先检查硬门槛，再用质量信号排序。任何一个硬门槛失败，都不能用 Star、作者知名度或模型主观评分抵消。

### 硬门槛

| 门槛 | 通过条件 | 失败处理 |
| --- | --- | --- |
| 真实来源 | 可访问的公开 GitHub 仓库和明确的 `SKILL.md` | `blocked` |
| 许可证 | 能核对到内容许可证 | `blocked` |
| 独立性 | 能单独触发并产出，不是 Agent 人设、Workflow、MCP 或整包伪装 | `blocked` |
| 任务适配 | 对应一个具体品牌营销任务，有明确输入和交付物 | `needs_manifest` |
| 安全边界 | 不自动发布、投放、付款、发消息、修改真实账户；危险动作有人工确认 | `blocked` 或 `needs_human_review` |
| 双端安装 | 在干净环境分别完成 Codex 与 Claude Code 安装 | `needs_install_test` |
| 实战交付 | 用脱敏 Brief 产生有用结果，并由人确认 | `needs_practice` |
| 案例与署名 | 有真实/脱敏案例、证据链接、上游作者和实践者署名 | `needs_practice` |
| 可玩说明 | 有 setup、如何开始、提示词和预期输出 | `needs_manifest` |
| 弯路与二创 | 有 pitfalls、best practices 和二创说明 | `needs_practice` |
| 使用深度 | 至少两个具体场景、适用边界、不适用反例和进阶路径 | `needs_practice` |

`integration_required`（例如需要 OpenSEO MCP）可以通过，但必须在详情页明确写出依赖、账号和可能成本；依赖本身不能被隐藏在安装命令里。

## 实战复核的二元量表

每项只记 `pass` / `fail` / `unknown`，不做 1–5 分平均：

1. 输入是否足够明确，第三方能复现实验；
2. AI 是否执行了 Skill 声称的具体动作；
3. 输出是否是可以继续工作的文件、表格、页面或清单；
4. 关键事实、证据和缺口是否被标出来；
5. 人必须决定的事项是否清楚；
6. 是否出现越权动作、无依据结论或凭空指标。

只有六项全部 `pass`，并有脱敏验证记录，`practice` 才能通过。

## 标准测试 Brief

- `BRIEF-SEO-001`：给一个公开网站、目标人群和业务目标，产出 SEO/AEO 诊断或关键词机会清单。
- `BRIEF-RESEARCH-001`：给一组脱敏评论/访谈和研究问题，产出原话、主题、证据缺口和下一步。
- `BRIEF-CREATIVE-001`：给一个虚构品牌活动和明确文字，产出视觉或内容方向，并检查事实、版权和渠道限制。

同一类候选必须使用同一 Brief，才能比较不同来源的 Skill。

## 共同维护节奏

- 每周至少提交 **5 个好用 Skill 评判记录**：提交时必须带齐来源、案例、署名、可玩说明、实践细节、场景边界和进阶路径，并进入人工复核队列；
- 每月公开不少于 **10 个好用 Skill**：只有全部硬门槛、案例、署名、可玩说明和实践细节通过，并由人工合并后才计数；
- “提交数”和“公开数”分开统计。评判器报告按当前 ISO 周/月输出两项目标和记录数，只有全部 gate 通过的记录才计入提交，周报补充本周新增、退回原因和下周要补的证据；
- 每个条目保留维护者、实践者、核验日期、来源 Commit 和复核 Brief，方便后续上游漂移时重跑。

数量是协作节奏，不是降低门槛的理由；当周不足 5 个合格候选，应明确标记缺口，不把未实践条目伪装成好用。

## 决策状态

- `blocked`：硬门槛失败，记录具体证据和不收录原因；
- `needs_source_review`：路径、许可证或上游内容还没有核对；
- `needs_manifest`：来源可以继续，但公开卡片信息不完整；
- `needs_human_review`：机器发现了外部写入、账号或其他风险，需要人工判断；
- `needs_install_test`：规范和来源通过，等待双端安装；
- `needs_practice`：安装通过，等待统一 Brief 实战；
- `ready_for_publication`：全部门槛通过，可提交 PR；
- `published`：已进入公开目录，后续只做上游漂移复核。

评判器只产生报告和建议，不自动把候选移动到 `catalog/skills/`，不自动合并 PR。
