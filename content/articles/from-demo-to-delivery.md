# 怎样做出可以交付的第一版

把输入、结果和验收接起来，让真实使用者完成一次任务。

:::takeaways 先看结论

- **第一版可以小，但任务要完整**：输入、处理、检查、结果必须接得上。
- **先写验收再选功能**，明确哪些情况要补材料或转人工。
- **让没参与制作的人独立试用**，记录卡点与维护成本。

读完完成：**首版交付说明**，别人知道怎样用，也知道结果怎样验收。

:::

*演示挑选理想条件；交付要面对真实输入。*

## 01 · 先约定结果，再划分功能

| 要写清 | 海报任务的示例 |
|---|---|
| 交付物 | 一组能编辑、能导出的门店素材 |
| 验收条件 | 价格、日期、尺寸正确 |
| 必需输入 | 门店信息、价格、活动日期与素材 |
| 停止条件 | 关键字段缺失，先补材料再生成 |

**“质量好”不是验收方式。** 资料摘要要能回到来源，海报要检查字段与导出结果；标准来自具体任务。

:::details 进一步理解 · 完整任务和验收标准

一个演示可以挑选最理想的输入，由制作者亲自操作，再展示最好的一次结果。真实使用时，这些条件往往不存在：资料可能缺字段，用户不知道下一步在哪里，结果还需要别人确认。第一版的目标，是让约定场景中的使用者完成一次完整任务。

范围可以很小，但前后必须接得上。用户从哪里提供输入，收到什么结果，怎样判断结果能用，失败时如何处理，都属于第一版。只缩减页面数量，却留下大量靠你临时解释的步骤，并没有真正降低交付复杂度。

本章会把上一章选出的需求转成一份首版交付说明。先用它检查流程，再决定哪些地方值得自动化。

用使用者的语言描述交付物：一份可编辑的内容计划、一个字段核对完成的表格、一组尺寸正确的素材。紧接着写验收方式。哪些内容必须准确，哪些允许人工调整，哪些情况应该停止生成并提示材料不足？

验收标准不要只写“质量好”“好用”。如果输出是海报，检查价格、日期、尺寸、可编辑性和导出结果；如果输出是资料摘要，检查结论能否回到来源、有没有漏掉重要限制。标准来自具体任务，不存在适用于所有 AI 产品的统一质量分数。

再列清输入要求。使用者必须准备什么，系统能够接受什么格式，哪些信息缺失会影响结果。能在输入时发现的问题，就不要等用户看完错误结果后才解释。

:::

## 02 · 走通一条最短路径

:::steps 输入 → 处理 → 检查 → 结果

1. **提供材料**：谁提交、接受什么格式、缺什么不能开始。
2. **处理**：系统做什么、人工做什么、预计要多久。
3. **检查**：谁按哪些标准判断，失败后如何处理。
4. **取得结果**：交付什么、怎样编辑或使用。

:::

先覆盖一个使用者的一种常见场景，列出暂不支持的情况。**只自动化重复且稳定的部分；人工介入也要可预期。**

:::details 进一步理解 · 怎样缩小首版范围

沿着“提供材料—处理—检查—取得结果”画出最短路径。每一步写出执行者、输入、输出和失败处理，优先覆盖最常见的一种使用情境。暂时不支持的情况明确列出，让使用者在开始前知道边界。

1. 选定一个具体使用者和一个触发场景。
2. 定义可检查的交付结果与必要输入。
3. 走完一次流程，记录所有需要临时解释的地方。
4. 只自动化当前最重复、最稳定的部分。
5. 让没有参与制作的人独立使用，再修正卡点。

人工处理可以是首版的一部分。重要的是谁来做、需要多久、怎样进入人工环节都可预期。自动化比例不是早期的唯一目标；一个可交付的半自动流程，往往比无人能验收的完整生成更容易得到真实反馈。

:::

## 03 · 在错误传下去之前安排检查

![小黑像裁缝一样检查并缝补纸张，再从交付窗口递出结果](/assets/from-demo-to-delivery-illustrations/02-check.png)
*检查与异常处理，本来就是交付的一部分。*

| 遇到什么 | 怎么处理 |
|---|---|
| 能确定的字段 | 用规则或原始资料核对 |
| 需要语境判断 | 安排人工确认 |
| 缺少依据 | 保留未知，提示补材料 |
| 处理失败 | 说明哪里未完成、结果能否用、下一步怎么做 |

:::case 教学假设 · 海报缺了活动日期

使用者提交了图片和价格，却没填活动日期。首版应指出缺失字段并请求补充，保留已填材料。

**不能为了填满海报，让模型猜一个日期。** 这是异常处理示例，不是已验证的产品案例。

:::

:::details 进一步理解 · 怎样阻止错误传播

AI 输出存在不稳定性，所以流程里必须有发现错误和停止错误传播的地方。把高代价错误提前列出，例如事实写错、敏感资料进入公开内容、价格错位。对这些错误设置明确检查，而不是统一加一句“请自行核对”。

检查可以来自规则、对照原始资料或人工确认。能确定的字段用规则核对；需要语境判断的内容由人确认；缺乏依据时保留未知。不要让模型为了填满格式而补齐无法确定的信息。

失败提示应告诉用户三件事：哪里没有完成，现有结果是否可用，接下来如何处理。重新提交、补材料、改用人工流程都可以，但不能只显示一个技术错误代码，让用户自行推断。

:::

## 04 · 独立试用，再决定下一次改什么

1. 找有该任务、没参与制作的人，观察他独立完成。
2. 分别检查正常、材料缺失、格式异常、结果不达标的样本。
3. 记录具体卡点，先修阻止任务完成的问题。
4. 记录人工介入、运行和维护成本，再考虑扩大使用。

**少量样本通过，不代表普遍可靠。** 资金、健康或重要业务决策场景仍需相应专业检查。

:::details 进一步理解 · 试用方法、维护成本与适用边界

找一位没有参与制作、但确实有该任务的人，给他正常输入材料，观察是否能完成。你可以记录他的停顿和提问，但不要在每一步提前提醒，否则检查到的是你指导使用的能力。

记录每个卡点发生在哪里：看不懂入口、材料不符合要求、结果无法编辑，还是不知道是否正确。它们对应不同修正。不要将所有问题都归为“提示词还不够好”，很多交付问题来自信息缺失、步骤安排或责任不清。

用少量有代表性的样本检查正常情况、材料缺失、格式异常和结果不满足标准的情况。样本通过并不代表产品普遍可靠，但可以说明哪些条件已经被检查，哪些仍未覆盖。

收到反馈后，先处理阻止完成任务的问题，再处理频繁重复的负担，最后讨论新能力。每项改动都要说明改善哪一步、如何观察改善；不能仅因为用户提到一个功能，就立即扩大范围。

还要记录每次人工介入、运行成本和维护原因。一个看似自动完成的服务，可能每天需要大量修复。若这些成本随用户量增长，就应在扩大使用前解决或如实计入交付方式。

本章的方法适用于验证首版工作流。涉及资金、健康或重要业务决策的产品，还需要相应领域的专业检查，不能因为一次流程跑通就扩大使用范围。

把范围、输入、验收、失败处理和责任人填进模板，让另一个人仅凭说明就能理解如何使用。最后问：正常情况能走完吗？异常情况知道怎样退出吗？结果有人能判断吗？这三个问题比功能清单的长度更能说明首版是否准备好。下一章再讨论怎样让更多匹配的人找到它。

:::

填模板前再问三件事：**正常能走完吗？异常知道怎样退出吗？结果有人能判断吗？**
